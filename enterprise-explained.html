ArcGIS Enterprise Explained

What you are being asked to host, in the terms you already use: a three-tier web application (web tier, application tier, data tier) that runs as Windows (or Linux) services — on one VM for teaching, or spread across several — listens on 443, authenticates against your identity provider, and is backed up with one command. Five diagrams, a hardware sizing guide (minimum → recommended → Esri-tested, and when a GPU actually matters), a pre-install checklist, the firewall table, an operations calendar, and a clear split of who owns what.

The 60-second version

What you are hosting

ArcGIS Enterprise is Esri's self-hosted web GIS — the on-premises counterpart to the ArcGIS Online SaaS. To a systems administrator it is an ordinary three-tier application: a web tier (your IIS or a Java web server, with two small Esri plug-ins), an application tier (two Java-based Windows services — Portal for ArcGIS and ArcGIS Server), and a data tier (an Esri-managed datastore, plus optionally a PostgreSQL or SQL Server database you administer). Users reach it over HTTPS on 443 through a single FQDN. It runs under a domain or local service account, writes to a handful of directories you should exclude from antivirus scanning and include in backups, and exposes health-check URLs you can wire into your existing monitoring.

Faculty will use it to teach GIS administration, so the students themselves will hold elevated roles inside the application (portal administrator, publisher). None of that touches the OS, the VM, or your network — the boundary between the application's administration and yours is one of the main things this document draws.

The base deployment

Four components, one job each

App tier · Windows service · :7443

Portal for ArcGIS

The website users sign in to. Holds the item catalogue, members and roles, groups, sharing, branding, and the security policy — including the SAML/OIDC connection to your identity provider. Java-based; stores its content in arcgisportal\content and its index/DB locally.

App tier · Windows service · :6443

ArcGIS Server

The service engine: runs the map, feature, tile and geoprocessing services that answer HTTP requests. Each service is one or more ArcSOC.exe worker processes — this is where CPU and RAM go. Licensed per CPU core. In the base deployment it is federated to the portal as its hosting server.

Data tier · Windows service · :2443

ArcGIS Data Store

Esri-managed storage behind the hosting server: a relational store (PostgreSQL under the hood — do not administer it directly) for hosted feature layers, and an object store for tiles, caches and files. Backed up via webgisdr, never by pg_dump.

Web tier · IIS module · :443

ArcGIS Web Adaptor ×2

Reverse-proxy plug-ins for IIS (or Tomcat/Java). One forwards /portal to 7443, one forwards /server to 6443, so only 443 is exposed and one CA-signed certificate on IIS covers the whole thing. Can be replaced by a load balancer or reverse proxy you already run.

Request & authentication flow

One click, five hops

Following one request explains where authentication happens and why the components must trust each other. Users authenticate once, to Portal — either with a built-in account or, as recommended here, via SAML redirect to your identity provider. Portal issues a token; the browser presents that token to ArcGIS Server with every service request, and the server trusts it because the two are federated. Nothing authenticates at the web tier unless you deliberately enable web-tier (IWA/PKI) authentication on IIS.

Data tier

Two databases, two ownership models

There are two relational databases in this design, and they are administered completely differently. The ArcGIS Data Store is a PostgreSQL instance that Esri installs, tunes, patches and backs up through its own tooling — treat it as an appliance: no direct connections, no pg_dump, no schema changes. Its backups are taken by webgisdr and its storage grows with whatever students publish as hosted layers. The enterprise geodatabase is a PostgreSQL (or SQL Server) database you stand up and administer like any other, into which ArcGIS Pro adds Esri's geodatabase schema; the server reads it in place for referenced layers. It is where versioning, SQL access and the database-administration parts of the curriculum live — and it is backed up by your normal DBA routine.

Architecture patterns

The same four pieces, three sizes

Separating tiers onto more machines changes nothing in the application — the components find each other by FQDN and the same ports. "Machine" means an OS instance, so those machines are usually VMs, and several of them can share one hypervisor host. Scale up (more cores and RAM on one VM) before scaling out; Esri's own guidance for small sites is to grow a single machine to ~16 cores before adding a second. High availability (two of each component behind a load balancer, shared file storage) is a legitimate size-2 pattern but is not needed for a teaching system whose downtime window is "between labs".

Target design

A reference teaching deployment

One VM in the institution's data centre or cloud tenancy, a PostgreSQL instance on the same VM (or on an existing DB server), SAML to the campus identity provider, a snapshot-plus-webgisdr backup routine, and an optional second VM that is powered on only for the imagery and notebook module weeks. Everything students administer lives inside the application; everything you administer lives outside it.

Hardware

How big a machine? Minimum, recommended, and Esri-tested

The most-asked question, and the one Esri deliberately half-answers: the documentation publishes installation minimums per component and then states that production hardware "is not listed because the user and business needs of the software may vary." So this section gives three anchored tiers — what Esri says is the floor, what Esri's own installer recommends for one machine, and what Esri's architects actually provisioned in a tested reference deployment — and then translates them for a classroom.

Tier 1 · Esri published minimum

  • 4 vCPU · 16 GB · 90 GB — the floor for a single-machine base deployment (installs and runs; will not carry a lab section).
  • Source: per-component minimums (Portal 2–4 cores / 8 GB; Server 8 GB; relational store 8 GB; object store 16 GB) and Builder's disk figures.

Tier 2 · Recommended · teaching VM

  • 8 vCPU · 32 GB · 150–200 GB SSD — Esri's own Enterprise Builder guidance is 32 GB for a standard single-machine deployment, 48 GB if hosted scene / 3D tiles layers are taught.
  • 8 vCPU at the usual 2:1 vCPU-to-core ratio = 4 physical cores = exactly the ArcGIS Server licence minimum.

Tier 3 · Esri-tested production reference

  • Portal 4 vCPU / 16 GB · Hosting server 8 / 32 · GIS Server 8 / 32 · Data Store 4 / 16 · Web Adaptor 2 / 8 · Database 16 / 64, each ×2 for HA, 128 GB disks (AWS M6i class).
  • Source: Architecture Center reference implementation (electric utility on PostgreSQL). The shape to grow toward, not the place to start.

Before installation

Pre-install checklist

Almost every painful ArcGIS Enterprise install traces back to one of these being decided after the software was installed. The FQDN and certificate in particular are baked into the configuration — get them right first.

  • Decide the FQDN nowe.g. gis.example.edu. Portal and Server record the hostname at configuration time; renaming later is a reinstall-grade change. Enterprise Builder does not support a DNS alias — install to the real hostname or use the manual component installs.
  • CA-signed TLS certificateIssued for the FQDN, bound to IIS 443 before the Web Adaptors are configured. Internal-CA certs work if every client trusts the CA; self-signed certs break ArcGIS Pro and mobile clients.
  • Service accountOne domain (or local) account, non-interactive, "Log on as a service", full control on the ArcGIS directories and any UNC data paths. Not a personal account; not a domain admin.
  • VM sizingStart at 8 vCPU / 32 GB RAM / 150 GB SSD — Esri's Enterprise Builder recommendation for a single-machine deployment (48 GB if 3D/scene layers are taught). Full tiers, disk layout and the GPU question are in How big a machine? above. ArcGIS Server licensing counts cores — 4-core minimum, 2-core steps — so agree the vCPU count with Esri Canada.
  • Operating systemWindows Server 2019/2022/2025, or RHEL/Alma/Rocky 8–9, Ubuntu 22.04/24.04 LTS. Fully supported on VMware, Hyper-V and cloud VMs. Time sync (NTP/domain) matters — token validation is time-sensitive.
  • IIS + .NETWindows path: IIS with the role features and the .NET Hosting Bundle version Esri specifies for the release. Install these before the Web Adaptor setup runs.
  • Firewall rulesInbound 443 from the campus/VPN ranges (80 if you want a redirect); management ports for you; nothing else. Outbound 443 for Esri licensing, patches and basemaps. See the table below.
  • Antivirus exclusionsarcgisserver, arcgisportal, arcgisdatastore directories and the ArcSOC/Java processes — real-time scanning here causes the classic "slow services, corrupt cache" tickets.
  • Licence files from My EsriPortal licence (.json, carries the user-type counts) and ArcGIS Server authorization (.prvc/.ecp) — downloaded by the licence administrator on the education agreement, via Esri Canada.
  • Identity provider metadataSAML metadata XML from Entra ID / ADFS / Shibboleth, and a decision on which attribute maps to the ArcGIS username (UPN or email). Portal is the SP; it publishes its own metadata for the IdP side.
  • Backup destinationA share or bucket outside the VM for webgisdr exports plus room for VM snapshots. The export can approach the size of the content directories — plan for ~1.5× content size.
  • PostgreSQL for the geodatabaseA supported PostgreSQL version (check the release's matrix) with the PostGIS or Esri ST_Geometry option, a database owner role for the sde user, and 5432 reachable from the ArcGIS Server machine.

Operations

The calendar

A teaching deployment has a rhythm a production system does not: the semester. Heavy use in weeks 2–12, a natural maintenance window between terms, and a "reset to clean" moment each term that most enterprises never get. Adjust the months to your academic calendar.

Daily · automated

  • Health checks: /arcgis/portaladmin/healthCheck (7443) and /arcgis/rest/info/healthCheck (6443) — HTTP 200 into your existing monitor
  • Disk free on the content, server and datastore volumes
  • Incremental webgisdr export (portal & hosted data) to the off-VM share

Weekly

  • Full webgisdr backup + VM snapshot
  • Skim ArcGIS Server logs for SEVERE/WARNING; run System Log Parser if a lab felt slow
  • Check the Esri patch notification tool; apply security patches in the next window

Each term · start

  • Restore the clean baseline (snapshot or webgisdr import) or rebuild via PowerShell DSC
  • Confirm SAML new-member defaults (user type, role, groups) for the incoming cohort
  • Create course groups; hand instructor accounts the Administrator role

Each term · end

  • Archive: full webgisdr export kept for one year
  • Script the account clean-up (unshare → transfer → delete); no SCIM yet, so this is Python against the portal API
  • Version upgrade in the break if a release is due (order: Portal → Web Adaptors → Server → Data Store)

Annually

  • Renew the TLS certificate (IIS binding and confirm Portal/Server trust it)
  • Rotate the service-account password (update all four services)
  • Review VM size against a term of System Log Parser data; check Esri's product life-cycle page for the installed version

Security & identity

Defaults to change, accounts to protect

Baseline hardening for the teaching VM

  • HTTPS only. Leave 7080/6080 disabled (default), force 443 at IIS, and set the portal's security setting to HTTPS for all communication.
  • Two break-glass accounts. The portal's initial administrator account and ArcGIS Server's primary site administrator are built-in, not SSO. Store both in the IT password vault; use them only for recovery and upgrades. Everyone else — including student "admins" — signs in via SAML.
  • Lock the admin URLs. Access to /portaladmin, /server/admin and /server/manager should not be reachable through the public Web Adaptor; keep them on the internal ports for IT only (the Server Web Adaptor has an explicit "enable administrative access" switch — leave it off).
  • Run Esri's scan scripts after install and after every upgrade: portalScan.py and serverScan.py ship with the software and report deviations from Esri's security best practices.
  • Anonymous access off. Students should sign in to see anything; a teaching portal has no public audience. Disable anonymous access and public sharing at the organization level (custom roles can withhold "share publicly").
  • Separate what students may break. Students get custom roles inside the portal (publish, manage own group content, no security settings) — not the built-in Administrator role, and never OS or VM access. If a student can take the portal down, the exercise is worth doing on a snapshot you can roll back in minutes.

Identity integration is SAML (or OpenID Connect) at the Portal tier only — there is no SCIM provisioning. Accounts are created at first login with the defaults you set; deprovisioning at term end is a scripted task. This is the single most common surprise for university IT teams.

Vocabulary

Terms that unlock Esri's documentation

TermWhat it means to an administrator
Base deploymentThe minimum working system: Portal + ArcGIS Server as hosting server + ArcGIS Data Store + two Web Adaptors.
MachineIn Esri's documentation, one operating-system instance — a VM, a cloud instance or a physical server. "Single-machine" and "multi-machine" count OS instances, not hardware: several VMs on one hypervisor host is a multi-machine deployment (isolated workloads, cleaner upgrades), though it is only highly available if paired VMs sit on different hosts.
FederationTrust between a Server site and the Portal, so Portal's users, roles, sharing and tokens govern the server's services. Set once, via /portaladmin.
Hosting serverThe one federated server that stores members' self-published layers; must have a Data Store registered.
Hosted vs. referencedHosted: data copied into the Esri-managed Data Store. Referenced: data stays in your registered geodatabase and is read in place.
Enterprise geodatabaseYour PostgreSQL/SQL Server database with Esri's schema added (the sde user and repository tables). Enables versioning, archiving, SQL.
Config-store & server directoriesArcGIS Server's configuration (JSON) and its working folders — cache, jobs, output, system. Local disk on a single machine; shared storage in multi-machine sites.
Content directoryPortal's file store for items (arcgisportal\content). Grows with uploads; the main thing webgisdr backs up.
ArcSOC.exeThe worker process ArcGIS Server spawns per service instance. Count × memory footprint is your RAM budget; shared instance pools reduce it.
TokenThe short-lived credential Portal issues at sign-in and clients present to Server; the reason Portal and Server clocks must agree.
Primary site administrator / initial administratorThe two built-in break-glass accounts (Server and Portal). Not SSO; vault them.
User type & roleUser type = the licence a member consumes (Viewer → Creator → Professional Plus) and which apps they get; role = permissions (Viewer, Publisher, Administrator, custom).
webgisdrEsri's command-line export/import of the entire deployment (portal items, hosted data, server config). Full or incremental; the backup tool.

Reference

Key facts & where to read more

Numbers worth remembering

  • Current version: ArcGIS Enterprise 12.1 (docs at doc.esri.com; 11.x remains documented at enterprise.arcgis.com and is what many institutions run).
  • Public port: 443 only. Internal: Portal 7443 · Server 6443 · Data Store 2443 / 9876 · PostgreSQL 5432.
  • Published minimums (12.1): Portal 2–4 cores / 8 GB / 30 GB; Server 8 GB / 10 GB; relational store 8 GB, object store 16 GB (32 GB free for better performance) / 13–27 GB disk; Web Adaptor 8 GB. Enterprise Builder recommends 32 GB RAM (48 GB with scene/3D layers) for one machine — hence the 8 vCPU / 32 GB / 150 GB teaching VM. No component of the base deployment uses a GPU.
  • Install: Enterprise Builder configures the whole base deployment in under an hour; PowerShell DSC or Chef make it repeatable.
  • Licensing: Portal by user types (licence .json); Server by CPU cores (4-core minimum, 2-core increments; hyper-threads don't count). Both included in the education agreement via Esri Canada.
  • Upgrade order: Portal → Web Adaptors → ArcGIS Server → Data Store (then re-run the scan scripts). Take a webgisdr backup and a snapshot first.
